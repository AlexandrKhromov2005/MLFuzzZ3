# 0056 — Встроенная композиция кампании с legacy-профилем

## Статус: accepted

## Контекст

Поручение владельца 2026-10-15 реализовать поэтапную миграцию из
[MODULARITY.md](../MODULARITY.md). База разработки — b8866b7. Публичный
перенос выполняется поверх da8f29d с сохранением отдельной истории
публикации (ADR-0055). Рабочие деревья
исследования не изменяются.

Цикл жёстко собирает детерминированную стадию и I2S+SMT; фабрика мутаторов
и random scheduler находятся в CLI. Это мешает менять отдельные политики.

## Рассмотренные варианты

- Универсальные динамические плагины — избыточная граница и нетипизированные
  контракты; отклонено.
- Одновременная смена алгоритмов и структуры — нельзя отделить регрессию
  поведения от изменения политики; отклонено.
- Поэтапная типизированная композиция с фиксированным legacy — принято.

## Решение

Сначала закрепляются недостающие трассы legacy; уже существующие проверки
не дублируются. Затем src/composition собирает именованные встроенные
мутаторы и SeedScheduler, включая round-robin. CLI отклоняет неизвестные
имена до запуска сервера. Random остаётся default с прежним RNG.

После первого слоя реализованы доменный ExecutionResult, сервис исполнения,
стадии и LegacyStrategyPolicy, версионированный YAML, capabilities, сборка
mutation-only без Z3 и составные havoc-операторы. Дешёвая I2S и обучаемая
политика добавлены отдельно от совместимого извлечения. Статус каждого шага
и границы профилей отмечены в MODULARITY.md.

При выделении ExecutionService бюджет должен проверяться перед каждым
исполнением, а наблюдения — принадлежать конкретному запуску. Подготовительный seed-run сначала сохраняет legacy
семантику; изменение его допуска/сохранения — отдельное решение. Публичные
include/fuzzer, wire-протокол и server-side frontier не меняются. Phase 3
не закрывается и продуктовый LLM-путь не вводится.

## Последствия

Добавление выбора сида или мутации не требует изменения CampaignLoop.
Рефакторинг проверяется trace-тестами, действующими campaign/concolic-тестами
и отдельными сборками с Z3 и без. Новые политики не наследуют утверждения о
производительности; научные сравнения требуют отдельных измерений.

Проверка конфигурации без Z3 выявила ошибку общего lint-скрипта: он передавал
clang-tidy исключённые solver/concolic-файлы без их compile commands.
Список для анализа теперь строится по compile_commands.json: проверяются
только действительно собранные production translation units. Это позволяет
проверять binding_provider.cpp без Z3 и независимо отключать регистрации
стадий. Regression-фикстура проверяет оба состава команд; это не заменяет
проверку сборки с Z3.

После полного переноса CampaignLoop владеет полиморфными компонентами через
unique_ptr и имеет обычный default-деструктор в любой конфигурации.
Regression-фикстура проверяет доступность уничтожения без солверных типов;
тривиальность деструктора больше не является свойством этого класса.

## Уточнение границ исполнения и совместимости

Рабочий CampaignLoop принимает ExecutionBackend с доменным ExecutionResult.
Исторический Runner и SessionRunner сохраняются как транспортный адаптер и
для существующих исследовательских утилит. Совместимый конструктор кампании
собирается в composition, а не в core. Доступ к LastBranchRecords остаётся
только внутри адаптера; генераторы получают принадлежащий запуску снимок.
ExecutionService проверяет лимит перед каждым реальным исполнением и перед
солвером. Общий обработчик явно сохраняет legacy-исключение подготовки:
сравнения исполняются и учитываются, но не меняют corpus/findings. Исправление
выхода за max_iterations между подготовкой и кандидатом является отдельным
наблюдаемым исправлением бюджета, а не обещанием идентичной трассы при лимите.

## Реализация переноса

Рабочие контракты находятся в core; совместимая сборка старого конструктора
и RunnerBackend — в composition. Deterministic возвращает прогресс, который
цикл сохраняет в существующем Corpus. Названия новых контрактных методов —
snake_case; существующие точки входа и фабрики первого переноса сохраняют
исходные имена для совместимости. Все физические запросы проходят через
некопируемый ExecutionService. Политики получают CorpusView/BudgetView,
генераторы — read-only вход и ограниченный сервис.

Разделены наблюдаемая новизна Go, admission и reward. Новые гибридные
профили явно включают обработку результатов подготовки; legacy сохраняет
старое исключение для подготовки и старый счётчик width-overflow. Новый
журнал всё равно показывает каждый запрос и типизированный solver_error.
Бюджетные отмены не выдаются за no_binding/SAT/UNSAT. Остаток времени
пересчитывается после построения системы/AST; пустые callbacks сохраняют
поведение исследовательского solver API.

ValueMatchBinding вынесен в библиотеку без Z3. Дешёвая I2S использует тот же
провайдер. Новые политики выбирают тот же набор генераторов; contextual
bandit — начальная экспериментальная реализация без внешней модели.
Два признака доступны до дополнительного исполнения: размер входа и
стагнация. Награда `(new_edges + 4 * findings) / max(1, execs)` учитывает
подготовку; SAT/UNSAT не награждаются. Действия выбирают mutation / I2S /
SMT с бюджетами 1/10/100/1000 мс в пределах конфига. Это не утверждение о
превосходстве над heuristic baseline и не открытие Phase 4.

YAML v1 строго проверяет поля composition, оставляя общий log отдельно.
Profile defaults < явный YAML < явно переданный CLI. Имена/сборка проверяются
до запуска сервера; возможности каналов — после handshake до исполнения.
Уровень журнала сравнения и отсутствие годной привязки — разные состояния.
Сохраняются параметры, revision, run_id, seed, capabilities и версии модулей;
журнал решений содержит запрошенные локальные бюджеты и реальные результаты.
CPU — только процесса контроллера; стеновой лимит не выдаётся за CPU-бюджет.

Независимые CMake-опции отделяют библиотеку решателя, регистрацию SMT и дешёвую
I2S. Campaign-эксперименты требуют зарегистрированной SMT-стадии; прямые unit
тесты солверной библиотеки доступны независимо от регистрации. Исследовательские
API и ABI IPC не меняют смысл. Публичные include/fuzzer не затронуты.

## Совместимость исторических бюджетных контролей

Полный прогон выявил, что минимумы прежних SMT-crash контролей измеряли
запрошенный лимит, при котором последний подготовительный запуск оставлял
нулевой остаток, но кандидат всё равно исполнялся. Например, опубликованное
18 соответствовало 19 фактическим исполнениям, 51 — 52, 83 — 84. Строгий
сервис намеренно не воспроизводит это превышение.

Исторические отчёты и цитаты не переписываются. Только ожидаемые значения
контролей, заканчивавшихся таким кандидатом, переводятся в строгие единицы
через явно названную test-only функцию `strict_terminal_budget`. Это не
универсальная формула для любого бюджета или первого вызова решателя.
В META указан переход единиц; каждый затронутый probe дополнительно проверяет
`execs <= max_iterations`. Эти прогоны служат регрессией переноса, а не новой
публикацией прежнего исследования или пересмотром его численных выводов.

## Сбор наблюдений по назначению исполнения

ExecutionBackend получает RunPurpose. Стандартный RunnerBackend материализует
журнал сравнений только при подготовительном запросе, резервируя итоговый
вектор по размеру снимка. Иначе каждый обычный mutation-run копировал бы
десятки тысяч записей даже при выключенных I2S/SMT. Это лишняя цена адаптера,
а не необходимая стоимость типизированного сервиса.

comparisons_available и comparisons_complete различают отсутствие сбора,
пустую полную трассу и частичный снимок. Новые стадии не могут использовать
отсутствующие наблюдения даже при allow_incomplete. Legacy оставляет прежний
no_binding/calls учёт неуспешной подготовки. Regression проверяет число
обращений к журналу, независимость запрошенных снимков, отсутствие канала
и старые счётчики ошибки. Протокол и фактическая инструментация цели не
меняются; публичный API этой внутренней сигнатурой не затронут.
